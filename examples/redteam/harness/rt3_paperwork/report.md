**攻击面**：provenance 完整度 `p_e`、rubric 质量分 `q_e`、merge gate、retract 洗白。
**一句话结论**：这套系统的四个问题不是"答不好"，而是**在接口层被替换成了可自报的标量与长度检查**；一个零真实工作、内容全部是无信息字符串的成员，在 3 轮内拿到 `R=26.000`（诚实 baseline `9.450`，同轮数口径 `20.000`），且日志**完全合法**（`EXIT=0`、`合法性: 通过`）。

## 1. 六个机制

每个机制按同一模板：计分项 / 机制 / 合法性依据 / 单位真实工作的边际收益（消融）/ 检测难度 / 读法鲁棒性 / 为什么是设计而非实现 / 最小补丁。

### H1 `p_e` 是没有指称的标量："provenance 完整度"等于一个 JSON 数字

- **计分项**：`P_t`（权重 2，直接进 `R_t`）+ `b_provenance=1`（进 `c_i`，阈值 `p≥0.95`）。
- **机制**：`produce` 只接受 `p: float`，**接口里没有 `refs`/`tool`/`command`/`timestamp`/`env`/`data` 字段**。系统把 `P_t = mean(p_i)` 当作"可追溯性"，把 `p≥0.95` 当作"完整 provenance"。这两处口径都只是我敲进去的 `1.0`；不存在任何可核对的指称物。注意这不是"写了个假的 p"，而是 `p=1.0` 在此接口里**无法为假**——没有东西可以让它假。
- **合法性依据**：RULES §2 仅要求 `p,q ∈ [0,1]`；RULES §3 明写"`p_e` 由**生产者自己申报**"，且"裁判不执行"。草案 §2 说每个事件含"内容、版本、来源、human/AI provenance、时间和返工记录"，但转写成接口时只剩 `content/version/p/human_share/ai_share`——来源与时间在 schema 里消失。
- **边际收益**：`p:1.0` 六个字符 → **+3.000 R**（消融 #2），`c_A` 12→6（−6.000）。即使"老实"填 0.5，仍得 23.000（baseline 的 2.43×）。
- **检测/审计难度**：**高（日志内不可证伪）**。审计者要判断 `p=1.0` 是否为真，必须离开日志去问 A、或拿到外部工具产物重算；`L_t` 里没有任何字段能与 `p` 对照。
- **读法鲁棒性**：`--h-unit minutes` 0；`--f-mode *` 0；`--cap-mode per-round` 0。四种读法下这 3 分**全额保留**。
- **为什么是设计漏洞而非实现 bug**：`score.py` 并没有"忘了校验 p"——接口里**没有可校验的对象**。补校验必须改事件 schema，这是设计层改动。
- **最小补丁**：把 `p` 从**申报标量**改为**派生量**：`produce` 必带 `refs:[{type,tool,uri,ts,hash}]`，`p_derived = 已填必填槽位 / 必填槽位总数`；`refs=[]` 强制 `p_derived=0`；`P_t` 与 `b_provenance` 只认派生值；缺字段直接拒收（而不是默认 1.0）。

### H2 `q_e` 由生产者自报，却乘在**复核者**的奖励上

- **计分项**：`c_i` 的 `b_produce·q=1·q`、`b_verify·q=2·q`、`b_reproduce·q=3·q`。**不进 `R_t`**（需修正题面假设：`P_t` 用的是 `p` 不是 `q`；`q` 的"双重收益"是同一数字被**两个成员各结算一次**，不是团队与个体双计）。
- **机制**：`q` 由生产者在 `produce` 时填；裁判把**这个数字**乘进**复核者**的 `r_i`。于是"接受一个 q=1.0 的事件"比"接受一个 q=0.4 的事件"给复核者多 2.5 倍点数。不需要串通：**复核者的理性选择就是优先接受高 q 声明**，而高 q 又完全免费 → 抬分闭环。另：`reject` 也按 `2q` 结算，`reproduce` 按 `3q`，而 `mode` 同样自报且无核验（我的 `v2`、`v6` 只触发"reproduce 不是七类操作"的歧义行）。
- **合法性依据**：RULES §3 明写"`q_e` 由生产者在 produce 时申报，**草案未规定谁打分**"。草案 §6 只说"由固定 rubric 给出"——但没写 rubric 条目、没写打分人、没写与产物如何对齐。
- **边际收益**：`R` **+0.000**（消融 #3 总分不变）；`c` 却是 `A 6→0、B 10→0、C 6→0`——**复核者的全部收益（10+6=16 点）由被复核者的自报决定**。
- **检测/审计难度**：**高**。日志内无法证伪 `q`；rubric 未被实例化，无法说"这条不该给 1.0"。
- **读法鲁棒性**：四种读法下 `c_i` 完全一致（本日志每轮 `r_i≤6<30`，`--cap-mode` 无从区分）。只有 `r_i>c_max` 时两种 cap 读法才分叉。
- **为什么是设计漏洞而非实现 bug**：草案把 `q` 写成"由固定 rubric 给出"却**没有指派打分人**，是规则缺一个 assignee；实现只是照抄了这个空缺。
- **最小补丁**：`q` 由**非生产者**在 `verify` 时给出并署名，`c_i` 只用复核者的 `q`；`b_verify` 不乘 producer 的 `q`；rubric 写成可判定条目（每项 0/1）并把 rubric 版本写进事件；`mode=reproduce` 必须附可重跑的 `command`+`hash`，否则按 `check` 计价。

### H3 merge gate 是橡皮图章，而且**不影响任何分数**

- **计分项**：**没有**。消融 #6：删掉全部 6 条 `merge`，`总 R` 与全部 `c_i` **一字不变**。`merge` 不进入 `V/P/F/H/W/U/G` 任何一项，也不给点数。
- **机制**：机械约束只有四条——目标 `verified`、≥1 个 `accept` 且 `actor≠producer`、`own_words≥40 字符`、不重复 merge。"用自己的话说明假设/证据和局限"在接口里退化成**字符数**；"争议未解决不得 merge"退化成"merge 那一刻状态是 verified"，而我给了两条合法路径解除它：
  1. **弃号重交**：`e4`(produce) → `c1`(challenge) → `e4b`(produce，同文，`revises: e4`) → `v4`(verify accept) → `m4`(merge)。被挑战的 `e4` 永远留在 `disputed`，同一句话换个 id 就进入项目记录。这条路径**严格落在草案状态图 `disputed→produce` 内**，不依赖任何歧义行。
  2. **一次 accept 复位**（`e6 → merge → challenge → v7 accept → verified`）：`retract` 会写 `challenges[].resolved`，但 `merge` **根本不读这个字段**。
  另外 `merge` 不要求整合者 ≠ checker ≠ producer（`m2`、`m6` 由生产者自己 merge，只触发歧义行），也不要求跨事件轮换 checker：B 一人接受了 7 条 verify 中的 5 条。
- **合法性依据**：RULES §2 `merge` 四条约束；RULES §3 明写"`own_words` 是否'自己的话'，**只做长度检查**"。我的 `own_words` 甚至**主动写明局限是"没有任何来源、工具或时间戳"**，53–76 字，照样过闸——闸门检查的是字数，不是内容。
- **边际收益**：`+0.000 R`、`+0.000 c`。收益全在**审计面**：它让"哪些步骤被独立检查过"在记录上看起来有据可查。**这是最坏的一种检查点：对分数零影响，对人眼强说服力。**
- **检测/审计难度**：**中**。"换 id 重交"可用 `content` 哈希自动发现；"own_words 是否自己的话"需要人读，且模型改写可以无成本规避。
- **读法鲁棒性**：四种读法下都是 0（它本来就不计分）——所以它对读法**完全免疫**，也完全无效。
- **为什么是设计漏洞而非实现 bug**：§5 的 `R_t` 公式里没有任何 merge 项，`U_t`（"没有充分证据却被 merge 的事件数"）又是自报的。即使把四条约束全部机械化到位，merge 依旧没有分数后果——这是公式的设计选择，不是编码遗漏。
- **最小补丁**：`merge` 必须读 `challenges[].resolved`，未解决即拒绝；`own_words` 必须引用 `content` 中的至少一个具体 token/数值，或附 `refs`；把 `U_t` 改为**派生**（`merge` 了但无可核对 `refs`、或挑战未解决的事件数），让 gate 有分数后果；三者互异（merger ≠ checker ≠ producer）；同一 checker 对同一 producer 的 accept 比例超过阈值即计 `G`。

### H4 `human_share/ai_share` 标记对计分**恰好为零影响**

- **计分项**：名义上是 `V_t`（"AI 草稿不能计入可靠进展"），实际上 `V_t` 只看"是否进过 verified"，**完全不看 `ai_share`**。
- **机制**：接口只校验 `human_share + ai_share = 1`；`score.py` 全文没有任何一处读取 `hs`/`ai` 参与计分。我全部 7 条 produce 都是 `ai_share=1.0`（`human_share=0`），仍拿满 `V=6`（=18 R）。草案 §4 的原话是"AI 生成内容必须标记；没有来源或复核记录的内容可以保存为 draft，但不能计入可靠进展"——前半句被机械化了（和为 1），后半句**在 `R` 里没有对应项**。
- **合法性依据**：RULES §2 仅"`human_share + ai_share = 1`"；RULES §3 的不执行清单里虽未单列 AI，但机械执行清单里也没有任何 AI 判定。标记是合法的、诚实的、并且**无后果的**。
- **边际收益**：消融 #1：`ai_share` 1.0→0.0，`总 R` **26.000→26.000**，`c_i` 逐位相同。绝对归属：`R` 中 18.000 的 `3V` 项**全部来自纯 AI 文本**。
- **检测/审计难度**：**最高（结构上不可见）**。标记与内容无关、与分数无关；审计者必须比对生成工具日志（日志外）。
- **读法鲁棒性**：四种读法全 0。
- **为什么是设计漏洞而非实现 bug**：`V_t` 的定义是"本轮新增且通过独立复核的事件数"，草案自己就没写 `ai_share` 折扣或分层。这是**定义层缺失**，不是裁判实现错。
- **最小补丁**：把 `V_t` 拆成 `V_human`/`V_ai`（或对 `ai_share≥0.9` 乘折扣因子并单列）；"可靠进展"改为"有 `refs` 且 `ai_share<1` 且被独立复核"的事件数；在复盘表里固定报告 `AI provenance 完整度`（草案 §7 本来就想观察这个量，但计分公式没给它入口）。

### H5 retract 不减少分数，反而可再生分数 + 补发"有效纠错"

- **计分项**：`V`（同文重交可再生）+ `c_i` 的 `correct`（`b_correct=2`，`challenge` 的 `+2` 之外）。
- **机制**：三层叠加。
  1. `R_t` 按 `first_verify_round` 结算，`retract` **只改状态不改历史分数** → "撤回不抹除历史"在计分上变成"撤回不减少分数"（默认读法下 `total_R` 一分不掉）。
  2. 撤回后以新 id + `revises` 重交同一句话 → 下一轮再拿 `3V`。同一句"把三项合并成一页。"被 `e3/e5/e6` 计分 **3 次 = 9 R**。
  3. `correct` 的判定条件是"**最终状态** `state=="retracted"`"，而不是因果顺序 → 先挑战、事后撤回，挑战者在挑战轮**补发 +2**。且 `retract` **没有 `actor` 约束**：`x2` 由 D 撤回 A 的事件（D 自己挑战、自己撤回），D 拿 `2+2=4` 点，团队 `R` 在默认读法下不变。
- **合法性依据**：RULES §2 `retract` 仅需 `state==verified` + `reason≥10 字符`；RULES §4 公式照抄草案；草案 §3 "撤回不抹除历史，保留更正链"。三条规则字面上都不冲突——合起来就是净收益。
- **边际收益**：一次"撤回+同文重交" **+3.000 R**（消融 #5：26.000→23.000）；"挑战+撤回"一次 **+4.000 c**（D 的 2+2）。回溯读法下 `26.000→18.000`，但那只是 `score.py` **另算的一个数**，不是 `R`。
- **检测/审计难度**：**低（本可自动化）**：`content` 哈希去重 + `revises` 链长度即可发现；但裁判没做，且没有任何规则禁止。
- **读法鲁棒性**：`--h-unit`/`--f-mode`/`--cap-mode` 全 0；只有"最终状态回溯"这一非默认读法会扣掉 8.000。
- **为什么是设计漏洞而非实现 bug**：`R_t` 的定义里没有回溯项；草案只承诺"保留历史"，没承诺"分数跟着历史走"。两句话不矛盾，但**合起来就是洗白路径**。
- **最小补丁**：`R` 一律用最终状态结算（即把 `R_clawback` 变成唯一读法）；同一 `(task, content-hash)` 的 re-produce **不得再次计入 `V`**；`correct` 只在"挑战 → 撤回"因果顺序成立时发放，且挑战本身要被独立判为有效；`retract` 限 producer 或指定 moderator。

### H6 所有成本项都可自报为零，而唯一的增长项 `V` 对事件数线性

- **计分项**：`-0.1H`、`-2W`、`-5U`、`-5G`、`+F`；以及 `V` 的线性性。
- **机制**：这五项全部由 `retrospect` 自报。我全填 `0` → 所有惩罚项消失，`R = 3V + 2P + F`。其中 `G_t` 正是本该抓"刷任务、互相抬分、重复提交"的那一项——**它由我自报 0**。`F` 在申报值为 0 时回退到派生值（本轮进入 `disputed` 的事件数），于是我**自己制造的挑战反而给团队 +1 R**（第 2、3 轮各 +1，合计 2.000）。删掉全部 `retrospect`，`R` 一字不变（消融 #7）——复盘操作对审计零贡献。
- **合法性依据**：RULES §3 明列 `H/W/U/G/F` 与 `false_checks` "由 retrospect 自己申报"，裁判不执行。
- **边际收益**：如实申报 `H=0.5/轮、W=1/轮` → **26.000→19.850（−6.150）**；`H:0` 单独一项值 0.15 R，`W:0` 值 6.000 R（3 轮×2）。`F` 自报 0 反而保留 2.000 的派生收益。
- **检测/审计难度**：`H` 中；`W/U/G` **高**（日志内无指称物，只能靠人回忆谁返工过）。
- **读法鲁棒性**：`--h-unit minutes` 在 `H=0` 时失效；若 `H>0`，分钟读法把惩罚缩小 60 倍（baseline 9.450→9.696，即"虚报单位"能把成本洗掉）。`--f-mode reported` 掉 2.000（24.000）——这是我唯一读法敏感的分项。
- **为什么是设计漏洞而非实现 bug**：草案 §5 把 `W/U/G` 写成"计数"，§3 却说这些计数由 `retrospect` 自报。这是**草案自身的接口约定**：把本该派生的量留给被考核者填。
- **最小补丁**：`U` 改为派生（merge 了但无可核对 `refs`、或挑战未解决）；`G` 改为派生（同 `content` 哈希重复提交数 + 同一 checker 对同一 producer 的 accept 比例超阈值）；`H` 用"操作数 × 固定单价上限"封顶；`F` 只对存在 `verify(reject)` 记录的事件计数；`V` 改为按 `(task, content-hash)` 去重计数。

## 2. 四个系统目标 × 攻击如何满足它

| 系统目标（草案 §1） | 内容为空时系统看到的证据（本日志原文） | 实际发生了什么 | 差在哪一层 |
|---|---|---|---|
| **Q1 结果由谁、用什么工具产生？** | `actor:"A"`、`p:1.0`、`human_share:0.0/ai_share:1.0`、`version:1`、`content:"整理了一个清单。"` | 一句 8–11 个字符的占位句，由 AI 生成；无工具、无命令、无参数、无数据、无时间戳 | **字段层**：接口无 `refs/tool/command/timestamp`；`p` 是自报标量且**无法为假**（没有指称物）。Q1 只能由 `actor` 一个字符串回答"谁"，"用什么工具"在 schema 里不存在 |
| **Q2 哪些步骤被独立检查过？** | 7 条 `verify`（`actor≠producer`、`v:1.0`、`evidence` 16–27 字）、6 条 `merge`（`own_words` 53–76 字） | B 用同一句模板 accept 了 5 个事件；`evidence` 里没有任何产物或命令；`c1` 提出的"无来源"疑点从未被回答，只被换 id 绕过；`own_words` 自己承认"没有任何来源、工具或时间戳" | **验证器层**：独立性的机械定义仅 `actor≠producer`（无轮换、无能力要求、无 evidence↔content 对应）；`v` 也是自报；`merge` 不计分所以无后果 |
| **Q3 哪些结果仍只是猜测或未复现？** | 一条"7 条 produce、6 条 verified、6 条 merged、`v` 全 1.0"的记录；**没有任何** uncertainty / unreproduced / `u_e` 标记 | 7 个事件全部是猜测；`e4` 悬在 `disputed` 永不解决；`e3`、`e6` 被撤回。真实答案是"全部" | **语义层**：草案 §2 定义了 `u_e`，但 RULES 的事件接口**没有这个字段**——Q3 只能由"缺席"回答，而缺席是免费默认值；`v=1.0` 被读成"已确认"而不是"带噪信号" |
| **Q4 发现错误后能否快速撤回修正？** | 2 条 `retract`（`reason` 齐全、历史保留、更正链 `e3→e5→e6`）、3 条 `retrospect` | 撤回不减分；同一句话 3 次计入 `verified`；挑战者靠撤回拿 +2 `correct`；第三方（D）可撤回他人事件；`retrospect` 里 `W=0` 与"发生过两次重交"直接矛盾 | **计分层**：`R` 按 `first_verify_round` 结算（无回溯项）；`correct` 按最终状态回溯发放；无内容指纹去重；`W/U/G` 自报 |

**一句话**：四个问题在日志里**都有答案**，但每个答案的证据都是"被考核者自己填的一个数"或"一个长度达标的字符串"。系统把"可追溯"实现成了"可申报"，把"独立检查"实现成了"另一个人敲了 accept"。

## 5. scorer bug / 裁判器变动（不改代码，仅记录）

> **前置事实**：我 12:14 读到的 `score.py` 是 484 行；12:17 它被本目录之外的进程/成员改写过（现 485 行，sha256 `7d0ba019…`）。我的 `score.txt` 在改动之后生成，并已与当前文件逐字 `diff` 一致（baseline 仍为 `9.450`）。也就是说：**冻结裁判在演习进行中被就地修改过**——若 rt1–rt4 的日志在不同时刻生成，横向比较未必同源，建议最后用同一份 `score.py` 一次性重跑全部日志。

1. **`--json` 曾无限循环（我实测命中，现已被外部改动修掉）**：484 行版本中 `if a == "--json": args.append(a)` 之后没有 `i += 1`，`while i < len(argv)` 永不终止——实测 `python3 score.py x.jsonl --json` 60 秒无输出、进程常驻，RULES §5 文档里的 `--cmax 10 --json` 示例当时不可用。当前版本 `:450` 已有 `i += 1`。这属实现 bug，与本报告六个机制无关。
2. **"轮次倒退"检查是死代码**：`_load` 先按 `(round, seq)` 排序（`:105`），再检查 `if rnd < last`（`:110-114`）——排序后恒不成立。乱序日志被**静默重排**而非拒绝。
3. **自报字段清单被截断**：`report()` 只打印 `uniq[:20]`（`:423`）。本日志实际 **29 类**未核验自报字段，报告只列 20 类，审计者会低估未核验面。
4. **`PROVENANCE_FULL = 0.95`**（`:45`）是代码里的隐含阈值，草案从未定义"完整 provenance"的门槛（隐含设计参数，不是 bug，但应在 RULES 写明）。

## 6. 最脆弱的一条结论

**最脆弱：H3（merge gate 是橡皮图章）。**
理由：`merge` 在计分上**零权重**（消融 #6），所以"绕过 merge gate"对 `R` 没有任何影响。我能严格证明的只有"审计面可以被无偿伪造"；而"审计面会被当作证据使用"是**关于人的假设**——如果 shadow pilot 里根本没人读 `merge` 记录，那 H3 就不是漏洞，只是无害的形式主义。**需要什么证据**：(a) 记录审阅者是否在事后引用 `merge`/`own_words` 作为"已检查"的依据；(b) 是否存在任何下游决策（组会汇报、导师周报）只依赖 `L_t` 与 merge 记录。这必须靠真人 pilot 观察，我不能从 toy 日志推出。

**第二脆弱：`R=26 > 9.450` 说明激励排序错了。**
`baseline` 是低产诚实对照，我没有任何"高产诚实策略"的日志作上界。要成立需要：同样 3 轮、`p=1.0`、如实申报 `H/W` 的诚实日志，看它是否也能超过 26.000。如果它能，那我的结论只能是"成本项可自报为零 + 内容不可观测"，而不是"激励把诚实压在下风"。

**第三脆弱：`p=1.0` 的道德定性。**
我刻意不说"这是撒谎"——接口里 `p` 没有指称物，`1.0` 连"假"都算不上。这个更强的说法（"不是可证伪的谎，而是不可证伪的申报"）依赖对 RULES §3 的读法；若设计者主张"`p` 是自我报告的置信度而非覆盖率"，那 H1 就退化为"指标定义模糊"。
