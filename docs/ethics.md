# 伦理与法律红线（ethics）

> 版本：v1.0（2026-10-19）
> 关联文档：[protocol.md](protocol.md)、[OPS.md](../OPS.md)
>
> 本文是**发布前检查清单 + 风险映射**，不是法律意见。具体案件请咨询律师或学校法务；
> 本文引用的法条与判例只用于提醒"哪些措辞会放大风险"。

## 0. 一句话

**只审计工件，不审计人；只陈述可复现的事实，让读者自己得出结论。**

审计报告的读者会把它当成对论文的负面评价，即使你写的每个字都准确。这意味着：内容真实只是及格线，**表达方式本身也是风险来源**。本文件的每一条都是为了把"指控"降级成"观测"。

## 1. 措辞规则

### 1.1 推荐句式

优先使用"条件 + 动作 + 观测"的句式，把结论留在读者那里：

```text
在 commit <hash>、命令 `<cmd>`、环境 <env> 下，claim "<论文原文>" 的检查未通过：
期望 <期望值/性质>，观测到 <实际值>，差异 <差值>（相对容差 <容差>）。
该结果限于本次运行；见 limits。作者回应见 README 附录。
```

更好的变体：

- "我们未能复现 Z"，而不是 "Z 是错的"；
- "本次检查中该性质不成立"，而不是 "该实现有 bug"；
- "在论文提供的设置下未观察到 X"，而不是 "作者隐瞒了 X"；
- "该数字与论文报告值不一致，原因可能包括环境差异、随机性、未披露的超参数；我们未能排除这些解释"，而不是 "结果对不上"。

### 1.2 禁止与替代

| 禁止 | 替代 |
|---|---|
| 造假、学术不端、篡改、剽窃、p-hacking（除非原样引用官方调查结论） | "未能复现" / "与论文报告不一致" / "在本环境下检查未通过" |
| 推断动机（"为了发论文"、"故意挑选"、"明显想掩盖"） | 只写事实；动机不在审计范围 |
| 夸张形容词：critical / glaring / blatant / severe / fatal / 严重 / 明显造假 / 触目惊心 | 数字、命令、差异、链接；让事实自己说话 |
| 评价个人：作者水平、导师、单位、过往工作、"某某也这样" | 只评论本次审计覆盖的工件 |
| 评价论文整体价值："这篇论文没有价值" | "本报告只覆盖列出的 claim；其余未测" |
| 标题党："顶会论文翻车"、"实测打脸" | 中性标题：`<论文标题>：C1/C3 两条数值 claim 的复跑记录` |
| 猜测作者不回应的原因 | 只记录"已通知，截至日期未回应" |

### 1.3 关键词自检（发布前必须跑）

```bash
grep -RniE "造假|学术不端|篡改|剽窃|p-hacking|critical|glaring|blatant|severe|fatal" \
  registry/audits/<slug>/README.md registry/audits/<slug>/report.md
```

命中不等于必须删，但每一条都要由第二签署人确认：是引用官方结论？是直接引语？还是应改写？

## 2. PubPeer 四条硬规则（本项目直接采用）

PubPeer 是"事后评审"领域运营最久、规则最成熟的平台。以下四条为本项目强制规则：

1. **禁止在报告中指控学术不端。** 不端行为的认定属于机构与期刊的调查程序，不属于审计者。
2. **只写事实、逻辑与公开可验证的信息。** 不使用未公开材料；不引用匿名传闻；每个判断都要能回到命令与输出。
3. **不评论作者个人，不推测动机与行为。** 审计对象是 commit、命令、输出，不是人。
4. **避免夸张形容词**（critical / glaring / blatant / severe / fatal…）。删掉形容词后如果句子还成立，就删掉形容词。

配套机制（同样采用）：

- 作者在报告发布前被通知（[protocol.md](protocol.md) §5）；
- 作者**永久回应权**：发布后仍可回应，回应原样收录，不因期刊更正或时间推移删除；
- 更正不删除历史：旧版本与 changelog 保留；
- 匿名回应/匿名举报先审核再发布（见 §7）。

### 2.1 truth defence 自检问题

> **"我们愿意为这条陈述在法庭上做真实性抗辩吗？"**

发布前，第二签署人逐条问报告里的每一句定性陈述。任何一句回答不了，就做三选一：

1. 补证据，直到能回答；
2. 改写成纯观测句（删掉结论）；
3. 删除。

这个问题比"读者会不会觉得过分"更重要：它检验的是**真实性抗辩能力**——你能否拿出证据证明自己说的是真的、没有歪曲、没有超出合理核实范围。

## 3. 中国法锚点（风险映射）

> 以下内容仅为自检提示，不是法律意见；条文以官方发布为准。

### 3.1 《民法典》第 1025 条

为公共利益实施新闻报道、舆论监督等行为，影响他人名誉的，不承担民事责任，**但**有下列情形之一除外：

1. 捏造、歪曲事实；
2. 对他人提供的严重失实内容未尽到合理核实义务；
3. 使用侮辱性言辞等贬损他人名誉。

对本项目的含义：

- 学术审计可以落在"舆论监督/学术批评"的讨论空间内，但**免责的前提是事实真实、核实充分、措辞不侮辱**；
- "捏造、歪曲"不只指数值错误，也包括**裁剪证据、只报不利结果、把不确定说成确定**；
- 措辞里的形容词、反问句、嘲讽语气都可能被认定为"贬损"。

### 3.2 《民法典》第 1026 条（合理核实义务的考量因素）

认定是否尽到合理核实义务，通常考虑：内容来源的可信度、对明显可能引发争议的内容是否进行必要调查、内容的时限性、内容与公序良俗的关联性、被批评者名誉受损的可能性、核实能力与核实成本等。

本项目对应的"合理核实"清单：

```text
[ ] 使用一手材料（论文原文、仓库 commit、可复跑命令），不依赖转述与截图传闻
[ ] 每条结论有可复跑证据，报告 hash 可被第三方核对
[ ] 已通知作者并给出回应窗口
[ ] 发布前第二人独立签署
[ ] 保留运行日志、环境记录、通知记录、回应原文
[ ] 措辞经过关键词与 truth defence 自检
```

### 3.3 《民法典》第 1028 条

被批评者有权要求更正、删除。对应本项目：**更正/撤回流程必须在报告里写清楚，且对作者请求给出时限**（见 [protocol.md](protocol.md) §6 与 [OPS.md](../OPS.md) 法务 playbook）。

### 3.4 耿美玉诉饶毅案（2021-12-14，上海浦东法院）的教训

公开报道显示：法院一审驳回原告请求，对学术批评持较宽松的态度，**但同时批评被告"言辞过激、方式方法不当"**；被告未被认定侵权，很大程度上是因为**已有官方调查结论**支撑其批评"并非毫无根据"。

对本项目的三条推论：

1. **"法院没判侵权"不等于"我们的写法没问题"**。判决里的"方式方法不当"本身就是警告。
2. **没有官方调查结论时，措辞必须比有结论时更克制**。我们绝大多数报告不存在官方结论，因此默认按"无结论"标准写。
3. **不要引用判例为自己壮胆**。报告里不出现"某某案判决支持学术批评"之类的话术，那会让报告显得像论战而不是审计。

### 3.5 默认身份策略

- 默认只写**论文标题 + DOI / arXiv ID + 公开仓库 commit**；
- **默认不点名作者、不写作者单位、不写导师、不写基金号**；
- 只有当作者单位/身份与结论直接相关（例如"该结论依赖作者未公开的私有数据"）时，才引用公开信息并注明出处；
- 通知作者用公开的通讯作者邮箱；报告中不公开邮箱、电话、地址；
- 不跟踪、不人肉、不访问非公开材料。

## 4. AI 使用规则

LLM 是本项目的工具，不是审计者。

1. **LLM 只能产出候选**：候选 claim、候选 check、候选措辞。所有 LLM 输出必须标 `HYPOTHESIS`，由人核实后才能进入 `audit.json`。
2. **verdict 不能由 LLM 给出**。verdict 必须绑定可执行检查（命令 + 输出 + 环境）；没有可执行检查的 claim 只能是 `NOT_RUN` 或明确标注的人审记录。
3. **报告必须声明 AI 使用范围**：用了什么工具、哪些部分由 LLM 起草、哪些结论由人核对。示例："claim 候选由 LLM 从论文摘要抽取，人工核对原文；所有 verdict 来自 `paperunit` 可执行检查；报告文字由审计者撰写并第二签署。"
4. **具名负责**：每个报告有具名审计者（可团队署名）与第二签署人；匿名报告不接受。
5. **禁止批量生成**：不得用 LLM 批量生成低质报告凑数。每个报告必须有真实运行记录与人工复核；违反者按行为准则处理（OPS.md）。

判断标准：如果把 LLM 换成一个实习生，你还会为这份报告署名吗？不会，就不要发布。

## 5. 第三方版权

- **不嵌入论文图表原图**。报告中只做最小必要引用：数字、公式、一句原文（加引号并标注出处）。
- 报告里的截图只用于展示证据（例如命令输出、报错信息），且限于必要范围；截图需注明来源。
- **不要给第三方内容套 CC 许可**。本项目的 CC-BY-4.0 只覆盖我们自己写的文字与图；代码为 Apache-2.0；引用的论文内容版权归原作者/出版方。
- 引用与评论的合理使用边界需要逐条判断；不确定时，宁可只引用数字与链接，不放整图。
- 作者或出版方要求删除引用片段时，配合处理（在合理使用范围之外的部分）；这属于法务 playbook 的一部分。
- 数据与模型：不重新分发论文的数据集/权重；只记录获取方式与 hash。

## 6. 利益冲突（COI）

必须披露的关系（包括但不限于）：

- 与被审作者同机构、同院系、同导师、同课题组；
- 近 3 年有合作论文、共同项目、共同资助；
- 师生关系、亲属关系、经济关系；
- 竞争关系：正在做同一问题、近期投稿到同一会议/期刊、评审关系；
- 个人恩怨或公开争论。

规则：

- 存在**直接 COI** → 不参与该审计（换人）；
- 无法换人（例如只有你会跑那个工具）→ 在报告显著位置披露，并把输出降级为 L1 复现记录，不作为 L2 报告发布；
- COI 声明写在报告 `README.md` 顶部，格式：`COI: 无 / 已披露：<关系>`。

## 7. 匿名与实名政策

- **默认署名**：当前维护者对外使用化名「无常」（细则见 §8）；其他贡献者默认实名（团队名 + 个人 GitHub handle）。
- **允许公开匿名、内部实名**：担心报复时，公开报告可署团队名/化名，但必须向 editor 与一名维护者披露真实身份；editor 对匿名审计者的身份保密，并承担签署责任。
- **不接受完全匿名且无内部背书**的报告；也不接受"匿名爆料"式投稿。
- 作者回应可以要求匿名（例如担心被网暴），editor 审核后发布。
- 举报/投诉通道：仓库 issue 模板或 editor 邮箱；处理过程不公开个人信息。

## 8. 化名与责任（当前维护者：无常）

项目以独立开源项目运营，对外署名为化名 **无常**；这是公开身份，不是匿名爆料通道。

### 8.1 署名规则

- 项目对外署名（README、release、年报、对外邮件）与审计报告署名使用化名「无常」。
- 其他贡献者按 §7 署名；多人共同署名的报告逐一列名，不把化名当"团队马甲"。
- 报告里的署名必须能对应到一个向 editor 披露过真实身份的维护者或贡献者；不存在"无人负责"的报告。

### 8.2 化名不产生免责

- 化名只改变公开身份，不改变责任：报告仍受本文件的措辞规则、证据要求、作者回应规则与 OPS.md 的治理流程约束。
- 若平台（GitHub、期刊、学校等）或法律规定要求核实身份，须向平台或司法机关披露真实身份，不得以化名对抗。
- 出现投诉、律师函或平台调查时，按 OPS.md §5 法务 playbook 处理；真实身份只给必要的处理人（editor、maintainer、法律顾问）看。

### 8.3 真实身份的保管

- 真实姓名与联系方式由**第二名维护者**私下保管（用于 bus factor 与法律联络），不写入仓库、不写进报告、不在公开渠道讨论。
- 在还没有第二名维护者之前，**不得发布点名单位的报告**（L2）；只能做 L1 复现记录或不点名的工具类报告。
- 第二名维护者离开时，按 OPS.md §6.4 交接清单把身份托管交给下一位维护者；交接记录本身不公开个人信息。

### 8.4 禁止化名滥用

- 禁止用多个化名伪造"外部复跑者""第三评审意见"或"DAO/评议会投票"；一个自然人在同一事项上至多一个署名、至多一票。
- 发现即按行为准则处理（OPS.md §4.6），并在 OPS.md 的季度记录中登记（不公开个人信息）；已发布的报告按 protocol §6 更正/撤回。

### 8.5 与治理流程的衔接

- 化名不改变 COI 规则：§6（利益冲突）与 OPS.md §4.5 的回避要求同样适用于化名成员。
- margin 政策讨论与评议会投票按 OPS.md §4.7 执行；投票记录使用公开化名与 `decision_id`，真实身份仅评议会内部核验，不公开。

## 9. 发布前 checklist（与 protocol.md §7 配套）

```text
[ ] 关键词扫描通过（§1.3），每处命中都有第二签署人确认
[ ] truth defence 问题对每条定性陈述都能回答（§2.1）
[ ] 没有推断动机、没有评价个人/单位、没有夸张形容词
[ ] 默认身份策略：不点名作者/单位（§3.5）
[ ] 署名使用化名「无常」或其他已披露身份（§7 / §8）；真实身份已向 editor 与第二名维护者披露
[ ] 已通知作者并记录日期；回应已原样收录或注明未回应
[ ] COI 声明（§6）
[ ] AI 使用声明（§4）
[ ] 第三方内容最小引用，未套 CC（§5）
[ ] 报告首页有"不是科学价值裁决"声明
[ ] report_sha256 可被第三方复跑核对
```

## 10. 违规处理

按情节从轻到重：

1. **提醒 + 要求修改**：措辞不当、缺声明、未通知作者（未发布前）；
2. **发布前阻塞**：第二签署人拒绝签署，报告退回；
3. **发布后更正**：已发布的违规内容 3 个工作日内修订，changelog 记录；
4. **撤回**：严重失实、侵犯隐私、明显违反本文件；
5. **移除贡献者权限 + 公开说明**：重复违规、批量低质报告、攻击性行为、用多个化名伪造外部复跑/评审/投票（§8.4）。

处理人：editor + maintainer（有利益冲突时回避）。保留处理记录，但不在公开渠道披露个人信息。
